# Roadmap

Forward view of CrossRev: what's in flight, what's next, what's deliberately deferred, and what shipped. Single source of truth for "what's next". Decisions of record live in [`adrs/`](adrs/).

## In flight

- **Prove automated mode end to end.** This is the `v1.0.0` bar and the reason the current tag is `v0`. Every command is covered by the offline suite and the local path has run against real pull requests, but **no repository has had the generated workflows installed yet**. What that proof has to establish: a real event chains one leg to the next through the label it applies, the composite action resolves and runs from a consuming repository, a credential restored from a secret authenticates, the watchdog catches a dropped event, and `yq` is genuinely present on GitHub's runner images. Until then, automated mode is built and unproven, and the docs say so wherever it comes up. The networked test tier that proof needs would also close a gap in the push guard. CrossRev warns when a `url.<base>.pushInsteadOf` rewrite redirects an approved push URL, and cannot refuse it. Refusing means validating effective push URLs, which every offline test that pushes would then fail.

## Next actions

- **The resolver merges the base branch** ([#113](https://github.com/carlosboeing/crossrev/issues/113)). Agents open pull requests in parallel, and the moment one merges the rest are conflicted. CrossRev cannot see that: `gh pr view --json` at `lib/github.sh:29` asks for neither `mergeable` nor `mergeStateStatus`. So `crossrev/converged` can be applied to a branch that will not merge, which is a label stating something false. Neither leg is broken by the conflict — the reviewer reads a three-dot compare from the merge base, and the resolver works in a detached worktree at the head SHA — which is exactly why the loop finishes and says so. The shape it takes: merging becomes the resolve leg's first duty, because the resolver is the pull request's author and merging is an authorship job. A four-rung ladder escalates from plain `git merge`, to a `merge=union` driver for append-only files like `CHANGELOG.md`, to the model, to a person. Mergeability becomes an input to `legs_should_continue`. The watchdog re-labels conflicted pull requests, since a base branch moving fires none of the pull-request events either leg waits on. The first shipment is detection and the convergence criterion alone, which gives no model any new authority.
- **`crossrev update`.** Today the update is `git pull` in the checkout and the uninstall is deleting it, which [installation.md](installation.md) states plainly because pretending otherwise is the failure mode. A real command would handle the pull, report what changed, and tell you when a config version has moved. An npm install already updates with `npm update -g crossrev-ai`, which narrows this to the clone rather than answering it — and leaves the config-version half unanswered either way.
- **`crossrev stop` and `crossrev resume`.** `crossrev/stop` is the loop's only human-facing kill switch. It is read in five places and written in one — the resolve leg applying it to itself after an escalation. So CrossRev can pull its own brake and you cannot, unless you reach for the GitHub label picker or a raw API call. The moment you need it is a leg mid-flight pushing commits, which is the moment you are least able to look up the syntax.
- **Kimi as a local harness.** Kimi is reachable today as a named endpoint on the Claude adapter. A native `lib/adapters/kimi.sh` would make the two legs different binaries, which removes the endpoint-variable hazard entirely, and it gains a skills-directory flag. What it costs, measured rather than assumed: no schema flag, no effort flag, and stdout that mixes narration and a resume hint around the payload with no way to isolate the answer. Local only either way — its credential is a 15-minute OAuth token.

## Future considerations

Everything here is deferred to the `v1.0.0` conversation, and all of it is a door deliberately kept open rather than a plan.

- **Revisit distribution.** `v0` installs by cloning, because `crossrev init` reads its action pin from `git rev-parse HEAD` and any route producing no `.git` leaves `init` unable to run. Going public and retiring the source-checkout delivery mode ([ADR 0009](adrs/0009-delivery-via-sha-pinned-composite-action.md)) removed the two reasons a tarball, a package or a formula was awkward, so the question is genuinely open again — it now depends only on giving `init` another way to learn its pin.
- **A compiled binary behind the same entrypoint.** `bin/crossrev` is the permanent entrypoint: `install.sh`, `action.yml`, the preflight and every doc go through it, so a compiled binary slots in behind it or replaces it under the same name with no consumer seeing the difference. The rewrite boundary is behavioural rather than structural — the offline suite drives the tool only through that entrypoint, stubbed `gh`, stubbed harness CLIs and throwaway git repositories, so it asserts what the tool does and never how it is written. The compatibility contract is four things: the CLI surface (commands, flags, environment variables, exit codes), the two JSON schemas, the marker and label contract, and the label namespace. The implementation language is not one of them.
- **Package the skills for harness plugin systems.** `skills/pr-review/` and `skills/pr-resolve/` are plain `SKILL.md` files, which is the packaging-agnostic source form. A plugin bundle or a marketplace listing is a later packaging of the same files; nothing in their content ties them to the current install path.
- **A second repository, on a trigger rather than a schedule.** `v0` is one repository by choice. The trigger for splitting is a second artifact with its own release cadence — a compiled binary versioned independently of the skills, or a plugin package with its own publishing cycle. Splitting is cheap and proven: this repository was extracted from a larger one with `git subtree split`, and joins work the other direction. Premature separation is its own cost.
- **Fork pull requests, and whether reviewing them is reachable.** CrossRev refuses every fork pull request. On a public repository that leaves it reviewing only the pull requests whose branch lives in the repository — a team's own, and Dependabot's. For a project taking contributions from strangers that excludes most of the inbound volume, which is also where review burden is highest. The refusal is correct as things stand and should not be removed on its own: GitHub withholds secrets from fork events, and a fork's head branch is not the base repository's to push to. What keeps the door open is that the usual objection does not apply here. **CrossRev never executes the pull request's code.** The generated review workflow checks out `refs/pull/N/head`, installs the harness, and runs the review action. It never runs the repository's own build, tests or install scripts, so the standard fork exploit — a malicious `postinstall` hook, a malicious test file — is not the exposure. The exposure is prompt injection: the diff is attacker-written text, fed to a model that has tools. Two mitigations already exist. The model process holds no GitHub credential, because the adapters strip `GH_TOKEN`, `GITHUB_TOKEN` and `GH_ENTERPRISE_TOKEN` before starting it ([ADR 0001](adrs/0001-cross-model-review-loop.md), `SECURITY.md`). The review leg is also read-only, with codex pinned to `--sandbox read-only` rather than left to a default. Two things have not been analysed, and they are the crux of any design. The harness credentials are passed as environment to the review step, so they sit in the leg's process environment while it reads attacker-controlled text — whether they are reachable from inside each harness's sandbox is unanswered. So is what network egress a model has under each harness's read-only mode, which decides whether anything read could be sent anywhere. GitHub's documented answer to this class of problem is the two-workflow `workflow_run` pattern: an unprivileged workflow handles the untrusted input and uploads an artifact, and a privileged one picks it up without ever checking out the head. It fits CrossRev better than it fits most tools, because the untrusted phase only has to produce a diff and needs no credential to do that. It does not answer the resolve leg, which pushes fixes to a branch the base repository does not own. So a fork pull request could be reviewed and not resolved, and whether half the loop beats none of it is an open question. The `issue_comment` path needs its own answer too, since it already runs privileged. This needs a threat model rather than a patch, which is why it is a door rather than a plan.
- **More reviewers, with different lenses.** The name encodes the mechanism rather than a count precisely so this survives ([ADR 0010](adrs/0010-name-crossrev.md)). Nothing is designed yet.
- **Measuring review quality, rather than asserting the loop works.** Every test CrossRev has asserts mechanism — a marker was written, a label moved, a thread was resolved — and deliberately never asserts what a reviewer found, because that is model output and varies between runs on the same diff. That is the right call for a test suite and it leaves a blind spot: nothing answers the question the config invites. Is one harness, model or effort level a better reviewer than another? Is a cross-vendor pairing actually catching what a single-vendor one misses? Those need a score over a fixed set of diffs with known defects, not a pass or a fail. The markers are already most of the raw material — each pass records the revision it reviewed, every finding, and the harness, model and effort that produced it. Worth building when there is a reason to choose between pairings on evidence rather than argument, which is not yet.

## Open questions

- **Does the offline suite need a second runner family?** CI runs on Ubuntu only. The tool is used on macOS daily and `init` renders workflows for both runner families, so a macOS job would catch a BSD-versus-GNU divergence that the Ubuntu job cannot. Worth doing when something breaks that way, rather than before.

## Recently shipped

- **Comparable cost telemetry** (2026-08-23). Each leg reported a duration and one token total built differently by every harness, so no two rows were comparable and an operator could not tell whether a pass was expensive. Every adapter now returns a normalized usage record — fresh input, cache read, cache writes split by TTL with an unsplit remainder for harnesses that do not name one, and output — with `total` defined as their sum rather than read from the vendor, because the vendor totals disagree about what they contain. Measuring all six harnesses on the same task found four live defects, fixed in the same change: agy's own total dropped its cache reads, opencode added reasoning to a figure already containing it, claude named whichever model sorted first on a mixed session and could fire the substitution warning on a healthy run, and the footnote under the table claimed no harness supplies a cost when two of them do. The run-details table gained Cached and Est. cost columns, the Agent cell names how the leg was paid for, and the estimate is priced from a vendored LiteLLM extract stamped with its upstream revision — preferring the harness's own figure, refusing unresolvable cache-write tiers and long-context breaks a cumulative total cannot rule out, and labelled an API equivalence rather than an amount charged.

- **opencode as a review-only harness** ([#111](https://github.com/carlosboeing/crossrev/issues/111), 2026-08-23). The fifth harness, and the first whose CLI constrains nothing: no schema flag at opencode 1.18.21, so the schema rides inside a copy of the prompt and the adapter extracts JSON from the NDJSON event stream down a ladder — bare, fence-stripped, then the span from the first `{` to the last `}` — spending the extra shape-retry that `schema_native: false` arms and nothing had ever called. Its permission defaults are inverted, most tools allowed out of the box, so an isolation config layered over the operator's own via `OPENCODE_CONFIG` denies edit and bash outright and `OPENCODE_CONFIG_DIR` at an empty directory keeps the operator's agents and commands out of the reviewing model; stdin is closed because with it open the CLI blocks printing nothing. One free session-export call supplies both the answering model and a whole-run token total, making this the third harness that can say what answered. A new `legs` field in the descriptor names which legs a harness may serve — absent means both — enforced before anything is staged or billed, so the resolve leg cannot name opencode and doctor says so up front. Staging also gained two things opencode's credential made reachable: honouring the previously-unread `assert_fresh` field, and creating nested staging directories under `XDG_DATA_HOME`.

- **Every run leaves a record on disk, and a failed leg keeps its transcript** ([#106](https://github.com/carlosboeing/crossrev/issues/106), [#107](https://github.com/carlosboeing/crossrev/issues/107), 2026-08-22). There was no log file anywhere: a 46-second stall inside the commit step was indistinguishable from a stall anywhere else, and a failed leg's diagnosis survived only in terminal scrollback. All four adapters also captured the harness's stdout and stderr and deleted both on every path, so the evidence of a wrong answer was removed by the code that noticed it. Every run now writes `run.log` under `~/.local/state/crossrev/runs/<repo-slug>/pr-<n>/<run-id>/` (the slash in the repository name becomes a hyphen) — one line per event, with exit codes and durations — and a failed leg keeps the harness transcript beside it, redacted before it lands. `--keep-transcripts` or `logs.keep_transcripts: true` keeps transcripts for successful legs too, and `logs.retention_days` (default 14) sweeps the whole directory by age. The generated workflows upload the directory as a run artifact, since the runner is discarded after the job; the pull request marker stays the durable record there.

- **The resolver commits without the repository's own git hooks** ([#104](https://github.com/carlosboeing/crossrev/issues/104), [#105](https://github.com/carlosboeing/crossrev/issues/105), [ADR 0017](adrs/0017-the-resolver-commits-without-host-git-hooks.md), 2026-08-22). It works in a worktree of the repository under review, and a worktree shares that repository's `.git/hooks/`. A GitHub-hosted runner clones fresh and has no hooks at all, so the same pull request behaved differently on a laptop. `git.hooks` now defaults to `skip`, and `run` restores them for a repository whose hook enforces something it relies on. A refused commit or push also carries git's own words into the error, which it previously discarded. A leg that dies records why, too. `_run_report_invoke_failure` had one caller, and every other fatal path left the claim marker reading `started` with a null reason. The report is mounted on the EXIT trap instead, so `crossrev status` reports the cause rather than inferring abandonment from a dead pid.

Grok as a fourth harness, seed-and-self-refresh credentials for the archetypes that support it, harness facts in one validated descriptor, the resolve leg in its own worktree, and the two hottest marker reads folded into a single `jq`. Automated mode is still built and unproven, so the version stays in `0.x`. Details in [`CHANGELOG.md`](../CHANGELOG.md).
- **v0.3.0 (2026-08-19)** — the entries below it, published. Findings named by location, descriptive resolver commits, fork pull requests from a terminal, a hosted leg that stops without its credential, and a push guard that reads every configured URL. Two breaking schema changes, allowed in a minor bump while the version is `0.x`. Automated mode is still built and unproven, so the version stays in `0.x`. Details in [`CHANGELOG.md`](../CHANGELOG.md).
- **A finding is named by where its code is, and the resolver's commits say what they changed** ([#43](https://github.com/carlosboeing/crossrev/issues/43), [#47](https://github.com/carlosboeing/crossrev/issues/47), [#48](https://github.com/carlosboeing/crossrev/issues/48), 2026-08-18). Both summary comments printed CrossRev's internal 16-character finding id at the reader, and it reached nothing: the id lives in an HTML comment marker, so it does not render, and a browser find matches only the row the reader started from. Findings are now named by `path:line` in a Location column, linked to the code from the review table and to the review thread everywhere else. Every commit a resolve pass pushed also carried the same hardcoded subject, so a pull request that ran four passes left four commits indistinguishable in `git log`. The resolver writes the subject now, following the repository's own convention, sampled from the base revision so a branch cannot seed the style of the commit written onto it. **`disposition` became `resolution` and `rebutted` became `disputed`**, in the schema and the code as well as the prose, because bug trackers have called this field a resolution for decades; markers written before the rename migrate on read.

- **Every configured push URL is validated before the resolve leg pushes** ([#36](https://github.com/carlosboeing/crossrev/issues/36), 2026-08-18). The guard read one push URL, and fell back to the remote's fetch URL when that was not a github.com address. A `pushurl` on another host therefore passed on an address the commit would never reach. The guard also saw only the first of several `pushurl` entries, while `git push` writes to all of them. Every configured push URL is now resolved to a slug and matched against the head repository. One that resolves to no github.com slug is refused rather than substituted.
- **A fully disputed or skipped pass converges instead of parking** ([#35](https://github.com/carlosboeing/crossrev/issues/35), 2026-08-18). A pass that settled every finding without pushing could never reach a terminal state — the reviewer declines an unchanged head — and `status` recommended exactly that declining command. The resolve leg now labels the settle converged, with the push rather than the resolution as the signal, and `status` reads the same rule off the marker for pull requests labelled before the fix.
- **An empty pass keeps `halted` while an escalation is open** ([#26](https://github.com/carlosboeing/crossrev/issues/26), 2026-08-17). A pass after an escalation files nothing — the reviewer does not re-raise a settled finding — and the label fallback read that as converged: a false green beside a marker reading issues-remain, on a pull request with verified defects still in the code. The empty pass now leaves the pull request halted, and the resolve leg and the cycle driver make the same call.
- **An escalated or blocked pass can be re-driven** ([#25](https://github.com/carlosboeing/crossrev/issues/25), 2026-08-17). Escalating completes a pass, and the resolve leg's re-run guard read completion — so the resume path for every halt a human is expected to clear declined with exit 0, and `status` recommended exactly that command. The guard now re-drives a pass that ended blocked or carrying escalations, and `status` tests for escalation first, counted across every pass.
- **`auth status` revalidates the App identity it reports** ([#5](https://github.com/carlosboeing/crossrev/issues/5), 2026-08-16). It read the name and slug from a file written once at registration and never checked them, so a rename went unnoticed — and the cached slug is what marker trust falls back to. It now reads `GET /app` with the JWT it was already minting, reports the drift, and corrects the cache.
- **v0.2.0 (2026-08-16)** — the four entries below, published. It carries the npm install route, the deliberate release process, and the two display fixes; automated mode is still built and unproven, so the version stays in `0.x`. Details in [`CHANGELOG.md`](../CHANGELOG.md).
- **`bootstrap.sh` is shellchecked** (2026-08-15). It was syntax-checked but absent from the shellcheck list, and it is the one entry script a stranger runs first — fetched from raw.githubusercontent and piped into bash. Being deliberately self-contained is what leaves it uncovered: it cannot source `lib/ui.sh`, so nothing else would catch a mistake in it. It was already clean at the severity the linter runs; the list now keeps it that way.
- **Generated App display names take the product name** ([#4](https://github.com/carlosboeing/crossrev/issues/4), 2026-08-14). `CrossRev <owner>` and `CrossRev Refresh <owner>` rather than the lowercase forms. The slug GitHub derives is unchanged, so marker trust is untouched, and `tests/test-auth.sh` now holds those two facts together.
- **Install from npm** ([ADR 0011](adrs/0011-npm-as-a-second-install-route.md), 2026-08-13). `npx crossrev-ai` runs the local loop with nothing cloned and nothing left behind. Automated-mode setup still needs a checkout, because `crossrev init` pins the action to a SHA it reads from CrossRev's own git directory — so npm carries the half that has run against real pull requests, and the half that hasn't stays where its proof will come from.
- **The pass label moves instead of accumulating** ([#2](https://github.com/carlosboeing/crossrev/issues/2), 2026-08-13). One grey pill, always the pass the pull request is on. A revision that resets the counter sheds the higher labels rather than keeping them as history — the markers are the record of what ran, the label row is the current state.
